# Phase 3: the Claude Code skill

The skill connects the engine (files only) to Figma (through the Figma MCP's `use_figma`, which runs
Plugin API JavaScript inside the file). Everything the skill does to token values goes through engine output.

## The transport problem

Data crosses between Figma and the engine only as text that Claude copies:

- **Export:** `use_figma` returns the variables, and Claude writes them to a file for the engine.
- **Push:** Claude passes the change set inside the `use_figma` code.

If one float is mistyped, the rule that "the agent never edits token values by hand" is broken without
anyone noticing. So every transfer is checksummed, and both ends verify it:

| Step | Produced by | Verified by |
| --- | --- | --- |
| Export | Plugin script returns `{ export, checksum }`, or `{ unchanged: true }` when the saved export still matches | `token-parity verify-export --figma <file> --checksum <c>` |
| Change set | `token-parity figma-script push` embeds the change set and its checksum | The plugin script, before it touches anything |
| Figma unchanged since export | The change set carries `basedOn.exportChecksum` | The plugin script re-exports and compares, refusing if Figma moved |
| Post-push state | The push returns the checksum of Figma's new export | `commit --push-result` compares it with the engine's predicted export |

The checksum is cyrb53 (53-bit, plain JS) over `JSON.stringify` of the parsed value, so whitespace and
pretty-printing don't matter. A transcription error is caught; it is never silently synced.
`commit` still checks a fresh export afterwards.

## Plugin code is generated by the engine

`token-parity figma-script export` and `token-parity figma-script push [--changes <file>]` print the exact
code to pass to `use_figma`. That code is built from functions in `packages/core/src/figma-bridge.ts`,
serialized with `Function.prototype.toString`. The plugin logic is therefore TypeScript and is unit-tested
against a mock `figma` global. The skill never hand-writes Plugin API code for token data.

- **Export:** local collections and variables (`remote` excluded), `valuesByMode` (colors `{r,g,b,a}`,
  aliases `{type:"VARIABLE_ALIAS",id}`), `scopes`, and `colorProfile` from `figma.root.documentColorProfile`
  (`DISPLAY_P3` becomes `display-p3`; `SRGB` and `LEGACY` become `srgb`, and `LEGACY` adds a warning).
- **Push:** verify the checksums, then resolve every target before any change: collections, modes,
  variables, alias targets. Then create, set and delete. If validation fails, nothing changes. The script
  returns the ids it created, updated and deleted.

## Scopes for new variables

The figma-use rules require explicit scopes, never `ALL_SCOPES`. The engine picks them, so they show up in
the plan:
1. the naming sibling's scopes, if it has the same type;
2. otherwise a default by Tailwind namespace: `color-*` gets fills, stroke and effect color;
   `spacing-*` gets `GAP` and `WIDTH_HEIGHT`; `radius-*` gets `CORNER_RADIUS`; `text-*` gets
   `FONT_SIZE`; `font-*` (string) gets `FONT_FAMILY`. The namespace says what a token is for, which is a
   stronger signal than which collection it lands in;
3. otherwise the scopes most common among same-type variables in the target collection;
4. If none of these apply, the scopes are left empty, and the plan says so.

`ALL_SCOPES` on an existing variable is Figma's default and usually means nobody set scopes, so it is
never copied.

`create-variable` gains `scopes`, and `add-figma` actions show them.

## Config: `token-parity.config.json`

The CLI reads it from the working directory (or `--config`) for defaults, so CI can run plain
`token-parity check`. Paths are relative to the config file. Explicit flags win.

```jsonc
{
  "figmaFile": "https://www.figma.com/design/AbC123/Design-System",  // used by the skill only
  "figma": "tokens/figma-variables.json",   // the export: committed, so CI can run check
  "code": "src/app.css",
  "lock": "tokens/tokens.lock.json",
  "resolutions": "tokens/token-parity.resolutions.json",
  "modes": { "dark": [".dark"] },           // optional; replaces the default mode map
  "figmaCollection": "Primitives",          // optional
  "nearThreshold": 0.005                    // optional; also rgbTolerance, precision, remBase
}
```

The export is committed because CI only runs `check` and the engine never calls Figma. The skill
refreshes the export, and CI checks code against the last one.

## Skill workflows (`skills/token-parity/SKILL.md`)

- **Setup** (no config yet): ask for the Figma file URL, the CSS file and where tokens should live, then
  write the config.
- **Check:** export, verify, `check`, then summarize. Read-only.
- **Sync:** export, verify, then `plan`. For each unresolved item, ask the user and record the answer in
  the resolutions file. Re-plan until nothing is unresolved or the user leaves the rest. Show the plan and
  get explicit approval (deletes need their own approval). Then `apply`. If there is a pending change set:
  `figma-script push`, `use_figma`, export again, verify, `commit`. Finish with a final `check`.

The skill writes only three files: the config, the resolutions file (the user's decisions), and the Figma
export (verified by checksum).

## Live test (2026-11-09)

Run end to end against a scratch Figma file through the Figma MCP. The run covered:
- a first sync with a decision and an approval;
- a second three-way sync with a conflict, a delete and a renamed variable;
- a concurrent Figma edit between plan and push.

Results:
- **Checksums:** four exports passed `verify-export`. The push refused the stale plan and changed nothing.
  Recovery (export, plan, re-approve) converged.
- **Float32:** Figma stores floats as float32 (0.223056 becomes 0.22305600345134735), as the mock assumes.
  The lock's RGB tolerance absorbs this.
- **Color profile:** new Figma files report `LEGACY`, so the warning is expected and is treated as sRGB.
- **Size limit:** `use_figma` caps code at 50,000 characters. `figma-script push` refuses larger scripts
  (about 300 operations) with a hint to sync in batches. Splitting one change set across several calls is
  future work: each part would need its own expected export, which the engine can't predict because
  Figma rounds floats to float32.
- **Large exports** are also bounded by what can be copied reliably. The checksum catches errors, but a
  file with thousands of variables would be slow to transfer.

## Token weight

Data that crosses the context costs tokens twice: once as the tool result, and once as output when it is
written to a file. Output tokens are the expensive kind. Three measures keep a sync small:

1. **Compact export (`token-parity/compact@1`).** Variables are grouped under their collection, with values
   in an array per mode. Constant id prefixes (`VariableID:`, `VariableCollectionId:`) are dropped, and
   `"!"` marks a raw id that lacks the prefix. Colors are `[r,g,b]`, with alpha only when it isn't 1.
   Numbers use their shortest float32 form, which is lossless because Figma stores float32. Scopes are
   sorted, because Figma reorders them. The result comes back as an object, not an escaped string. The
   adapter still reads the full REST-like format.
2. **Unchanged exports cost nothing.** `figma-script export` embeds the saved export's checksum. If Figma
   still matches, the plugin answers `{ unchanged: true }` (about 40 tokens) instead of the data.
3. **No export after a push.** The push returns the checksum of Figma's new state. `commit --push-result`
   predicts that export from the pre-push export and the change set (float32 numbers, new ids from the
   push result). If the checksums match, the engine writes the export itself. If not, the skill does a
   normal export. A wrong prediction can't be committed.

`verify-export` rewrites the saved file in one canonical layout (2-space JSON), so git diffs read the same
whoever wrote it.

Measured on the live test file: 118 → 54 tokens per variable per mode for a changed export, and 37 tokens
for an unchanged one. For 300 variables in two modes, that means:

| | Before | After |
| --- | --- | --- |
| `check`, Figma unchanged | about 70k | about 1k |
| `check`, Figma changed | about 70k | about 33k |
| Sync | about 140k (two exports) | about 35k (one export plus the push script) |

## Matching by codeSyntax

A Figma variable's `codeSyntax.WEB` is the designer's own record of its name in code, so it is the
strongest matching signal. Keys come from, in order: `codeSyntax.WEB`, then the lock's variable ID, then
the name rule (`a/b/c` ↔ `--a-b-c`).

- **Names come from an exact `var(--x)`** (with an optional fallback argument) or a bare `--x`, after
  stripping the Tailwind prefix. The prefix comes from `@import "tailwindcss" prefix(ds)` or the
  config's `prefix`. The name counts only if code has it. Otherwise there's a warning and the variable
  falls back to its name. If it is then missing in code, `plan` adds it under the `var()` name, which
  is the designer's choice.
- **Identifier-shaped forms.** Tailwind utilities (the prefix maps to a namespace, and the variable's
  type tells `text-` color from font size), Sass `$x`, Less `@x`, camelCase and dotted JS paths only
  produce candidates. They match when exactly one exists in code. If none matches, `plan` asks
  (`code-syntax-unmatched`) instead of guessing a CSS name.
- **Anything else is not a name.** Expressions (`calc(var(--ds-spacing) * 4)`), literals (`2px`) and
  arbitrary values (`bg-[#fff]`) fall back to the name, with one combined info note per check instead
  of a warning each.
- **Prefixed runtime names.** With a prefix, Tailwind emits `--ds-…`. Mode overrides written with that
  name (`[data-theme="dark"] { --ds-color-surface: … }`) are overrides of `--color-surface`. New
  overrides and new Figma code syntax are written with the prefix.
- **Remaps.** A `codeSyntax` that resolves to a different key than the lock records is reported as info.
  Two variables resolving to one key is an error.
- **New variables.** Variables created from code get `codeSyntax.WEB` set in the file's majority direct
  style (`var(--x)` by default). The export carries it as `code`, only when set, and the post-push
  prediction includes it.

## Real-project fixes (Tailwind `prefix(ds)`)

- **`var()` references in CSS use the emitted names.** Tailwind doesn't rewrite them, so code writes
  `--color-accent: var(--ds-color-green-500)`. A reference whose unprefixed name is a theme token reads as
  that token, in `@theme` and in mode blocks alike. Prefixed names that aren't theme tokens are left as
  written.
- **Namespace resets** (`--color-*: initial`, `--*: initial`) aren't tokens.
- **Alias against literal.** When exactly one side is an alias, both sides are compared by resolved value,
  so `{dark/fg-1}` and `#e9edf0` are equal. Lock entries record the resolved Figma RGB. A side counts as
  unchanged if either its alias or its resolved value matches the lock. A Figma alias copied to code
  whose target isn't a CSS token is written as its resolved value, never as a dangling `var()`. Two
  aliases still compare by target.
- **Single-mode Figma vs code mode overrides.** A token in a single-mode Figma collection is compared on
  its default only. Each extra code mode is `missing-mode` ("Code defines a dark value, but Figma
  collection 'Primitives' has no dark mode"), which `plan` leaves for the user (`figma-mode-missing`).

## Ignore list

`ignore` (config, or `--ignore`) takes patterns matched against a token's CSS name or Figma variable name
(`animate-*`, `dark/*`). `pattern:mode` ignores one mode only (`color-amber-*:dark`), for intentional
code-only dark overrides of single-mode primitives. Ignored tokens and modes aren't compared, planned or
written to the lock (existing lock entries are kept as they are). They stay in the token sets, so aliases
to them still resolve. A check reports how many were ignored, as info.

## Color format in code

Colors are always compared in OKLCH. `colorFormat` only decides what `apply` writes into CSS:
- **`"preserve"` (default).** A replaced value keeps its format and style: hex case, and legacy
  `rgba(r, g, b, a)` vs modern `rgb(r g b / a)`. New tokens use the file's majority format; ties go to
  oklch, then hex.
- **`"oklch"`, `"hex"`, `"rgb"`.** Always that format.

Hex and `rgb()` hold only sRGB. A Display P3 color inside sRGB is converted. One outside sRGB is written
as `oklch()`, with a note on the plan action. The lock keeps OKLCH whatever is written: the text itself
for `oklch()`, or a lossless OKLCH rendering of hex/rgb. So 8-bit rounding never shows up as drift. The
"not oklch()" warning only appears under `"oklch"`.

## Exact color matching (default)

The requirement: colors need 1:1 parity with Figma. If Figma shows `#0000FF`, that is the value to find in
code.

- **`colorMatch: "exact"` (default).** Both sides are reduced to 8-bit sRGB bytes (r, g, b, alpha), the
  way Figma shows them, and must be identical. There is no tolerance and no near-match. Lock change
  detection uses the same bytes.
- **Notation.** A matching color written in a form you can't search for (`oklch()`, `hsl()`, named) is a
  `format-mismatch` error, suggested Figma to code. `plan` rewrites it as hex or `rgb()`: "preserve" keeps
  hex vs rgb() per value, and replaces oklch with the file's majority of hex/rgb, defaulting to hex.
- **Writing to Figma.** Code's bytes are written as k/255, so Figma displays exactly the code's hex.
- **Display P3 files** fall back to perceptual matching with a warning: Figma's hex there is P3, which CSS
  hex can't express.
- **`colorFormat: "oklch"`** with exact matching is refused as a configuration error.
- **`colorMatch: "perceptual"`** is the earlier behavior (OKLCH ΔE, near-matches, `oklch()` allowed). The
  original fixtures in `test/fixtures` and `test/plan-fixtures` describe this mode and run with it
  explicitly. Exact-mode fixtures live in `test/exact-fixtures`.

## Aliases to different variables; computed values (Real-project round 3)

- **Aliases.** Values compare by what they resolve to unless both sides alias the same variable, which is
  equal by structure. Figma `{gray/900}` vs code `var(--color-on-fill)` → `var(--color-gray-900)` is in sync
  when both reach the same color. Retargeting an alias to an equal-valued variable is not a value change.
- **Code aliases resolve in the runtime mode.** A single `@theme` value `var(--color-green-100)` resolves to
  the `.dark` override of `--color-green-100` when the dark pair is compared, as the browser would.
- **Computed values.** A Figma variable whose codeSyntax is `calc(var(--x) * n)` (or `n * var(--x)`) gets a
  read-only computed code value, n × `--x` (prefix stripped), when code declares `--x` but not the token.
  It compares normally. Figma → code fixes are unresolved (`computed-in-code`); code → Figma works. A check
  reports the count as info.

## Real-project round 4: scales + semantics

- **Naming through codeSyntax siblings.** A sibling matched by codeSyntax shows how keys map to names
  (`green/500` ↔ `color-green-500`: drop `color-`), so `color-green-900` becomes `green/900` in the sibling's
  collection, with its scopes and codeSyntax.
- **`color-mix()`** is evaluated per mode (premultiplied alpha, normalized percentages, oklch hue methods),
  with `var()` operands resolved in that mode. Unsupported forms warn and aren't compared. It's exempt from the
  exact format check, and `plan` won't overwrite it (`computed-in-code`).
- **`alias-mismatch`.** When both sides alias different variables with the same value, that's a finding
  instead of silence. The direction comes from the lock's per-side aliases; without them it's a first-sync
  decision (`--prefer` applies). `plan` re-aliases, creating targets first and resolving pending aliases by
  name.
- **Alias validity.** Before proposing a Figma alias, `plan` checks that it resolves to code's value in that
  mode: directly for existing targets, and after planning for created ones. If not, it writes the value, with
  a note.
- **Lock shape.** New entries always store the resolved value (`oklch` + `figmaRgb`, or `value`) plus
  `figmaAlias` / `codeAlias` for sides that alias. The older `{ alias }` form is still read, as "both sides
  aliased this".
- **Info notes.** A `calc()` codeSyntax that is evaluated against code is no longer also listed under
  "doesn't name a CSS token".
